# PacketWatch roadmap

What the project cannot do yet, and what would fix it.

Every item here traces back to a limitation that was **measured**, not guessed
at. The numbers quoted come from the evaluation reports in this repository, and
each entry names the report that justifies it. Anything that cannot be justified
that way belongs in a wish list, not in this file.

---

## Where the project stands today

Phase 1 delivered a working detection and prevention system: live capture, two
classifiers, rule verification, automatic Windows Firewall blocking, explainable
alerts, bounded memory, and three public-dataset evaluations.

It also produced an honest list of what the system cannot do. That list is the
starting point for everything below.

| Measured limitation | Evidence | Addressed by |
|---|---|---|
| Slow DoS, web attacks and botnet C2 detected at 0% | `EVALUATION.md` per-attack table | Phase 2 - A |
| Models collapse to F1 0.05-0.22 across datasets | `TON_IOT_EVALUATION.md` | Phase 2 - C |
| Deployed models trained on synthetic traffic | `UNSW_EVALUATION.md` | Phase 2 - C |
| One machine sees only its own traffic | design | Phase 2 - B |
| No alert history beyond a rotating log file | `docs/er_diagram.png` is a design, not an implementation | Phase 2 - Tier B |
| IPv4 only (the capture filter is `ip`) | `capture.py` | Phase 2 - Tier B |
| Blocking is all-or-nothing | `response.py` | Phase 2 - Tier B |
| No way to see what the system is doing without reading a terminal | - | Phase 1.5 (done) |

## Phase 1.5 - the dashboard (built)

Shipped as `packetwatch/dashboard.py` and `dashboard.html`, behind
`--dashboard`. Seven panels; the three marked below are the ones specific to
this project. Panels 8-10 are still open.

```
python -m packetwatch --simulate --dashboard          # no Administrator needed
python -m packetwatch --dashboard --iface "Wi-Fi"     # live
```

### Panels

**Core** (built)

1. **Status bar** - running state, interface, uptime, packets/sec, sources
   tracked, and a clear DRY RUN badge when blocking is disabled.
2. **Active blocks** - IP, blocked at, a live countdown to the 30 minute expiry,
   the reason, and an unblock control. The countdown makes the TTL visible;
   today it is a safety feature nobody can see.
3. **Alert feed** - newest first, HIGH and CRITICAL colour-coded, each showing
   the explanation string already generated by `verify.py`.
4. **Traffic over time** - packets/sec, with block events marked.

**The panels specific to this project** (built)

5. **Decision funnel** - sources seen, ML flagged, rule confirmed, blocked. One
   widget that shows the whole architecture: the gap between "flagged" and
   "blocked" is the verification layer doing its job.
6. **Flagged, not verified** - the near misses. What the system deliberately
   chose not to act on, and which rule it fell short of.
7. **Per-source drill-down** - the 10 live features as bars against their
   thresholds, e.g. `51 ports [########..] limit 10`.

**Operational** (not yet built)

8. Rule hit breakdown - which of the three rules fires most.
9. Threshold panel - current values, whether they are defaults or calibrated,
   and a calibrate control.
10. Protected addresses - this machine, the gateway, the whitelist, so their
    absence from the alert feed is explained rather than mysterious.

### Constraints that must hold

All four held; the tests in `tests/test_dashboard.py` check the first three.

- **Bounded memory must survive.** A fixed-size ring buffer for recent history;
  anything older is read from the already-rotating `alerts.log`. A dashboard
  that accumulates history in memory quietly undoes the strongest engineering
  result in `BENCHMARK.md`.
- **The capture path must not be touched.** The dashboard reads a snapshot. It
  must never block the sniff loop, and the 34,000-45,000 packets/sec figure has
  to hold with it running.
- **Bind to 127.0.0.1 only.** A dashboard with an unblock control is a control
  surface, and it should not be reachable from the network.
- **No build step.** A small HTTP server plus one page. A node_modules folder
  would contradict the lightweight claim this project rests on.

## Phase 2 - candidate directions

Three substantial options. One or two of them is a phase, not all three.

### A. Layer 7 inspection - close the payload blind spot

**Fixes:** 0% detection on slow DoS (slowloris, GoldenEye), web attacks (brute
force, XSS, SQL injection) and botnet C2, documented in `EVALUATION.md`.

These attacks arrive on ports 80 and 8080 at ordinary rates, so no threshold on
packet headers can separate them from real browsing. Catching them means looking
at something other than volume and port spread.

Approaches, easiest first:

- **Connection-behaviour features.** Slowloris is invisible to packet counts but
  obvious in connection duration and in how many half-open connections a single
  source holds open. New features, same architecture.
- **HTTP request inspection.** Request rate per URL, unusual methods, injection
  patterns in query strings. Covers web brute force and injection.
- **TLS fingerprinting (JA3/JA4).** Identifies the client software without
  decrypting anything. Botnet tooling has distinctive fingerprints while looking
  like ordinary HTTPS.
- **Suricata or Snort as a third verification source**, alongside the existing
  rules rather than replacing them.

**Why it is defensible:** the boundary was found by measurement and published in
our own report before we extended past it.

### B. Multi-host deployment - cross-host correlation

**Fixes:** a single machine only ever sees traffic aimed at itself.

Lightweight agents on several machines reporting to one collector. The payoff is
detection that is arithmetically impossible in v1: an attacker probing 3 ports
on each of 5 machines trips nothing anywhere, but 15 ports network-wide is
plainly a scan.

Work involved: an agent and collector protocol, a shared view of source
reputation, coordinated blocking so one host's detection blocks the attacker
everywhere, and a decision about how much agents trust each other.

**Why it is defensible:** a real architectural change, and it demonstrates well -
several machines, one attacker, one coordinated block.

### C. Self-training - let the rules supervise the models

**Fixes:** the cross-dataset collapse to F1 0.05-0.22, and the reliance on
synthetic training data.

The threshold rules are deterministic and correct when they fire. So use
rule-confirmed detections as labels and retrain the classifiers on the host's
own real traffic. The explainable layer teaches the statistical layer.

This is the principled answer to an honest finding: models do not transfer
between networks, so they should adapt to the network they are deployed on. A
trustworthy label source is already built into the system.

Work involved: a labelling policy (rule-confirmed as attack, long-quiet sources
as normal), guards against feedback loops and label drift, periodic retraining
with rollback if accuracy drops, and an evaluation showing that adaptation beats
the shipped model on the deployment network.

**Why it is defensible:** the most genuinely publishable of the three. It is a
contribution rather than an integration.

### Tier B - substantial supporting work

- **Adversarial evaluation.** Attack the system deliberately: scans slow enough
  to stay under the thresholds, scans spread across source addresses, spoofed
  sources. Measure what gets through, then harden. Attacking your own system
  carries more weight with a panel than another accuracy table.
- **SQLite alert history.** The ER diagram in `docs/` is a design that was never
  implemented. Implementing it makes that diagram real and unlocks trend views
  in the dashboard.
- **IPv6 support.** The capture filter is IPv4 only. Not glamorous, but a real
  gap a reviewer may find.
- **Graduated response.** Rate limit before blocking outright, a quarantine
  mode, and an automatic packet capture of the attack for forensics. Less
  collateral damage than the current all-or-nothing block.
- **Threat intelligence feeds.** Check source addresses against known-bad lists
  as an extra verification signal - a known malicious address could block on one
  rule instead of two, the way the vulnerability risk map already does.
- **Remaining base-paper datasets.** Edge-IIoTset, and WUSTL-IIoT-2021 if a
  mirror becomes available, to complete the base paper's dataset set.

### Tier C - productization

Windows Service so it survives a reboot, an installer, a tray icon, scheduled
automatic calibration, a signed release. Low research value, high "this is a
real product" value.

---

## Recommended combination

**A + C, evaluated by adversarial testing.**

These three fit into one story:

> Phase 1 measured exactly what the system could not see. Phase 2 extends
> detection into that blind spot, replaces synthetic training with traffic
> learned from the deployment itself, and validates both by attacking the
> system deliberately.

That is a research narrative. "We added five features" is a changelog.

**If a strong demonstration matters more than a strong paper**, swap C for B.
Several machines coordinating a block in front of a panel is hard to beat.

## Keeping this file honest

Two rules:

1. **Nothing enters this file without evidence.** A limitation belongs here once
   a report, a benchmark or a failed test demonstrates it. Until then it is a
   suspicion.
2. **Record the questions you could not answer.** Every review produces
   questions that expose a real gap. Written down as they happen, they become
   the next phase's scope - proposed, in effect, by the people evaluating it.
